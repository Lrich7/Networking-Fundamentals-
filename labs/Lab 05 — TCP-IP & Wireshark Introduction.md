# 🧪 Lab 05 — TCP/IP & Wireshark Introduction

Welcome to **Lab 05 of Networking Fundamentals**.

```text

   ↓
```

# 🧭 Understanding the Wireshark Interface

Wireshark is divided into several important areas.

---

# 1️⃣ Packet List

The top section displays captured packets.

Common columns include:

```text
No.

Time

Source

Destination

Protocol

Length

Info
```

Each row represents a captured packet or frame.

---

# 2️⃣ Packet Details

The middle section lets you expand protocol information.

You may see sections such as:

```text
Frame

Ethernet II

Internet Protocol Version 4

Transmission Control Protocol
```

or:

```text
User Datagram Protocol
```

---

# 3️⃣ Packet Bytes

The bottom section displays the raw packet data.

You do not need to understand the raw hexadecimal information yet.

For now, focus on:

> **Packet Details**

# 🔄 Part 10 — Observe TCP Conversations

Use the filter:

```text
tcp
```

Look at the:

```text
Source
Destination
```

columns.

You should notice traffic moving in both directions.

Conceptually:

```text
Client
  │
  ├──────> Server
  │
  <───────
  ├──────>
  │
  <───────
```

TCP communication is a conversation rather than a single one-way packet.

---

# 🤝 Part 11 — Find the TCP Three-Way Handshake

TCP usually establishes a connection using:

```text
SYN
   ↓
SYN-ACK
   ↓
ACK
```

This is known as the:

> **TCP Three-Way Handshake**

---

# 🔍 Look for SYN

You can try the display filter:

```text
tcp.flags.syn == 1
```

You may see SYN and SYN-ACK packets.

Another useful filter is:

```text
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

This focuses on initial SYN packets.

---

# 📝 Identify the Handshake

If your capture contains the beginning of a TCP connection, find:

### Step 1

```text
SYN
```

### Step 2

```text
SYN-ACK
```

### Step 3

```text
ACK
```

---

# 🧠 Conceptually

```text
CLIENT                         SERVER

   SYN
    ─────────────────────────>

             SYN-ACK
    <─────────────────────────

   ACK
    ─────────────────────────>
```

After this, application data can be exchanged.

# 🌎 Part 14 — Local MAC vs. Remote IP

Suppose you're sending traffic to:

```text
8.8.8.8
```

The destination IP may be:

```text
8.8.8.8
```

But the destination MAC in the Ethernet frame will not normally be the MAC address of Google's remote server.

Instead, the local frame typically uses the MAC address of:

> **Your default gateway**

Why?

Because Ethernet handles:

> **Local-link delivery**

The router handles getting the IP packet toward remote networks.

|---|---|

| Layer 6 — Presentation | Encryption / Formatting concept |

| Layer 3 — Network | IPv4 |

| Layer 1 — Physical | Wi-Fi / Ethernet signal |

# 🔐 Why Does HTTPS Look Strange?

If you're examining HTTPS traffic, the application data should largely be:

> **Encrypted**

You should not expect to see the actual website content in readable text.

That's a good thing.

The traffic is protected by technologies such as:

> **TLS**

---

# 🧠 Important Lesson

Packet capture doesn't automatically mean:

> "You can read everything."

Encryption protects application data.

However, packet captures may still reveal useful metadata such as:

- IP addresses
- Ports
- Timing
- Protocols
- Connection behavior
- Packet sizes

# 🛠️ Troubleshooting Challenge 3

You see:

```text
SYN
SYN
SYN
```

from a client with no SYN-ACK response.

What might that suggest?

Possible areas include:

- Server unreachable

> **The client is attempting to establish a TCP connection and isn't receiving the expected reply.**
